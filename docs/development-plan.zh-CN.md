# COD 资产名称发现工具：开发方案

日期：2026-10-02。本文保留最初设计快照。当前 2.1.0 的实际实现、P0–P2 验收及测量见 [实施记录](adaptation-implementation.zh-CN.md)，使用说明见 [教程](user-guide.zh-CN.md)。当前发布为本地 Windows EXE 安装包，支持没有研究项目与开发运行时的新电脑。

## 1. 专业判断与产品范围

项目可行，应定位为“基于关键词、命名语法及资产证据的名称发现工作台”。关键词本身不能从哈希中推出完整原文，核心价值是减少候选空间、持续运行和严格验证。不同游戏、资产类型可能使用不同哈希域，因此不能设计成一套通用 FNV 算法覆盖所有 COD。

用户最新确定范围：所有非模型资产，材质可选排除；未命名模型不进入发现目标。已知模型名保留为关键词及候选语料。

首版支持：导入现有资产目录与名称词典；关键词搜索已知名称；自动学习并生成候选；CPU 后台查找；自动验证；冲突管理；Saluki CDB 导出。GPU 作为可选加速后端。模型内容导出、游戏内运行时提取和完整 FF 解包不进入首版，直接利用研究项目已有目录。

要明确区分三个动作：查询已有名称、发现未知名称、导出验证名称。用户输入 `mike4`，先看到现有模型家族，再选择规则尝试未知名称。未知资产不能直接按“真实名称包含关键词”过滤，因为真实名称尚不可知；关键词约束的是候选，目标集合来自模型类型、构建、包范围和未知哈希。

可复用本地模块：

- `analysis/resolve_asset_names.py`：词典导入、规范化与两种种子回算参考。

不直接修改已有研究数据库。新程序保存独立工作数据库和目录快照指纹。本地 resolver 包含低 60 位候选查表及未回算词典分支，新程序不能将这些分支当作最终验证成功。

## 3. 推荐架构与技术选型

推荐 PySide6 GUI + Python 调度层 + Rust CPU 核心/导出辅助程序 + 可选 CUDA 计算模块 + SQLite。PySide6 相比延续 tkinter 更便于实现大型表格、排序筛选、设备设置与托盘交互；这是新产品的工程选择，已有 tkinter 工作台仍可独立使用。

Python 用于规则编排、文件适配、任务管理与 GUI，不负责高吞吐逐字符哈希循环。Rust 核心既提供批处理接口，也提供独立 worker CLI；优先以子进程 JSONL 协议连接，便于故障隔离和打包。GPU 采用 NVIDIA CUDA 作为本机优先实现；OpenCL 留作后续 AMD/Intel 支持，首版无需同时维护两套 GPU 内核。

数据流：

```text
资产目录/名称数据库/本地字符串
           ↓
导入验证 → 构建与算法配置 → 目标哈希集合
           ↓
关键词 → 词法切分/家族语法 → 有限候选计划
           ↓
CPU 或 GPU worker → 命中队列 → CPU 独立回算
           ↓
目录与类型核验 → 冲突检测 → 工作数据库
           ↓
CSV/CDB 导出 → 回读检查 → Saluki 实际加载验收
```

核心模块职责：catalog-adapter 只理解输入目录；hash-profile 只定义规范化与哈希；candidate-engine 定义可重放的候选空间；worker 执行范围；verifier 决定是否接受；exporter 负责格式；GUI 通过任务服务读状态，不直接操纵 worker 内存。

## 4. 查找策略

按成本和证据强度安排任务阶段：

1. **前作映射直接复用与已有映射回算**：cod-name-db、WNI、本地已知名称先做去重，按来源作品的 hash profile 回算验证；完整名称键存在于本作所选资产目录且没有冲突时，直接进入可导出集合。此路径不要求名称再次通过本作算法回算，也不进入候选穷举；保留来源作品、算法及本作目录命中证据。其余新生成候选按本作目标 profile 验证。
2. **本地字符串**：读取已产生的字符串索引、解压名称匹配记录、清单；只使用来源可追踪的字符串。
3. **家族扩展**：从包含关键词的已知名称抽取前缀、插槽及后缀，按同类型与同构建学习。
4. **有限规则组合**：部件、视角、LOD、版本、数字编号、分隔符；规则必须有界，可预估总候选量。
5. **受限字符搜索**：仅针对确定的未知片段、长度和字符集，默认不启用无限全字符组合。

已在本地看到 `att_rex_vm_ar_mike4_barhvy_v0`、`att_rex_vm_ar_mike4_mag_v0`、`att_rex_vm_ar_mike4_irons_v02` 等模型名，可学习 `att_rex_vm_ar_{weapon}_{part}_{variant}` 家族。但不能强行用一个模板覆盖全部名字，`v02` 与 `v0` 要视作不同文本。

规则输入支持关键词 AND/OR、用户别名词典、前后缀、限定插槽、数字范围、最大长度、目标包和候选上限。别名应由数据库证据或用户提供；玩家常用武器名称不一定等于内部开发代号。

命中后可学习同一家族的新片段，但必须限制反馈轮数、新增规则数量及候选预算，防止一个结果触发无界扩展。生成器使用稳定规则编号与混合进制候选编号，断点只需保存已完成区间，不保存所有候选字符串。

先用普通规则组合，之后评估前缀状态复用或 meet-in-the-middle。不能把完整 64 位 FNV 的可逆性质直接套到被截断的 63 位结果；中间相遇需要正确处理隐藏位和完整状态，必须独立验证收益。

## 5. 哈希配置与自动验证

本地 `resolve_asset_names.py` 的算法参考：UTF-8 字节逐个异或后乘 `0x100000001b3`，每步按 64 位溢出；种子分别为 `0x47f5817a5ef961ba`、`0xcbf29ce484222325`；最后 `& 0x7fffffffffffffff`。输入已有小写化与反斜杠转正斜杠操作。

每个 profile 必须记录游戏/构建/名称域、种子、编码、大小写规则、斜杠规则、输出掩码、测试向量和证据来源。保留原始字符串和规范化字符串。先证明该 profile 能回算本构建真实样本，再用于查找；非 ASCII 大小写规则不能未经确认就使用 Python Unicode lower 作为游戏行为。高位标志与名称键另存，避免丢失原始键。其他哈希域后续用独立插件添加。

验证链：

1. worker 输出候选编号、规范化名称、profile 和完整命中键。
2. CPU 参考实现独立重新计算；GPU 结果不能直接进入最终导出。
3. 与构建快照里的完整目标键一致，且目标资产类型处于任务范围。
4. 同哈希不同名称、不同来源不一致时进入冲突区，不覆盖现有映射。前作复用采用下述专门规则，不强制再次通过本作算法回算。
5. 保存来源、规则、构建、包、时间及验证器版本。

状态分为候选、回算匹配、目录验证通过、前作验证且本作命中、额外载荷证据、冲突、拒绝。默认导出目录验证通过或前作验证且本作命中、并且无冲突的映射。额外载荷或依赖关系是加强证据，不必强制重解压全部文件。

### 前作已验证映射的直接输出规则

根据用户要求，设前作映射为 `(H, N)`：用对应前作与名称域的算法、规范化及有效位宽验证 `Hash_source(N) == H`，再确认相同完整名称键 H 存在于本作目录。通过后直接输出 `(H, N)`；无需生成候选、GPU 搜索或本作算法再认证。算法可以跨作品不同，来源 profile 必须独立保留，不能将此状态误写成“本作算法已回算”。

完整名称键指其名称域定义的有效键，并保留原始值及标志位；仅低 60 位相同不满足条件。目标仍遵守所有非模型资产、材质可选排除的范围；类型来自本作目录，来源类型已知时检查名称域是否对应。不同来源同键异名进入冲突区；仅扁平化音频导出名不能替代已验证的原名称。

记录 source_game/source_build/source_profile/source_hash/source_name、来源词典指纹、source_verified、target_build/target_asset_type/target_hash、target_present 及验证版本。GUI 单列“前作复用”，统计与本次新发现分开。关键词筛选可在已验证前作名称上执行；导出支持选定关键词结果或全量复用结果。首次导入验证后可缓存，profile 或词典指纹改变则重新验证。

验收用例：前作回算成功且本作完整键存在时直接导出；即使本作 profile 回算不同也保留此合格复用状态；前作回算失败、本作不存在、仅低位匹配或同键异名均不自动导出。导出保留本作键和前作验证名称，旁表说明来源及复用条件。

这验证的是“名字与资产哈希相符”，不能数学上证明唯一历史原文；大小写/斜杠规范化也可能无法恢复原始书写形式。界面应称“已验证名称”，保留这一含义。

排除材质是类型过滤：不以名称包含 `mat` 判断。默认所有已支持的非模型类型；未知哈希域标为待适配并禁止假验证。xmodel 从发现目标排除，`material` 单独开关；image 是否排除使用独立选项。未知类型保留标识。筛选影响目标集合和导出集合；使用材料中的字符串作词典证据可以单独设置，不等于输出材质资产。

## 6. GPU 与性能策略

CPU 先作为正确性基线，使用多线程、批量哈希及内存目标集合，禁止每个候选查询 SQLite。GPU 内核在设备上由候选编号生成字符串，只传字典、模板、目标表与任务区间；只回传命中记录，避免逐条传字符串。

按任务类型和包范围分别测排序表二分、开放寻址表；目标规模大时评估 Bloom filter 加精确集合。Bloom 命中不能替代完整比对。命中缓冲区溢出时标记本批失败并重跑或分页，不能静默丢弃。

支持 CPU / GPU / 自动模式；自动模式用小型校准任务比较端到端速度，考虑初始化及生成成本。FNV 是逐字符依赖的整数运算，大 GPU 并不保证所有任务更快。记录候选/秒、时间/新增已验证名称、传输耗时和峰值内存，不能只展示内核速度。

后台模式设置 CPU 线程数、GPU 批次/占空比与时间预算；若可读设备遥测，展示温度和利用率，否则显示不可用。Windows 显示 GPU 上的内核应保持短批次，根据驱动响应调节，避免长时间独占。驱动重置、OOM 或编译失败时保存断点并提示，可回退 CPU。

性能验收基于实测，禁止预设“几十亿次/秒”。任务预计候选数 `N=各插槽数量乘积`，校准吞吐 `R` 后显示约 `N/R` 的范围估计；运行中调整。候选量过大时先让用户缩小规则或设置预算。

## 7. 后台任务、数据库与可靠性

GUI 关闭时可选择隐藏到托盘继续工作；明确退出时询问暂停保存或终止。后台 worker 必须由长期存活的托盘宿主管理，不把隐藏窗口误称为 Windows 服务。首版不默认安装服务或开机启动。

任务状态：排队、运行、暂停请求、已暂停、验证中、完成、预算耗尽、取消、失败。搜索空间跑完而没有命中也是正常完成，界面给出已覆盖规则范围，不说名称不存在。

SQLite WAL + 单写入队列，批量提交命中与任务进度。只有命中完成验证并提交后才将对应批次标为完成；崩溃恢复允许少量重复工作，通过唯一约束保证幂等。task 保存目标快照、profile、字典与规则指纹、设备、版本、预算；恢复发现指纹改变时创建新任务或保持旧快照，不能悄悄继续。

建议表：builds、hash_profiles、assets、asset_occurrences、names、evidence、dictionary_sources、rules、tasks、task_ranges、hits、conflicts、exports。资产身份至少 `(build_id,asset_type,name_hash)`；名称映射允许跨类型共享，但证据按资产保留。哈希存 8 字节 BLOB 或固定 16 位 HEX，避免 SQLite 有符号整数与完整 u64 冲突。名字冲突以 `(profile,export_key)` 检查，因为 CDB 的映射键未必包含资产类型。

仅存命中、审计与范围进度，不保存每个失败候选。源词典记录提交 SHA/文件校验值和导入时间；更新先写临时版本并验证，再切换快照。CSV 导入检查空名、NUL、异常换行、错误哈希和重复冲突，提供拒绝统计。

## 8. GUI 方案

采用桌面研究工具布局，支持浅色/深色、中文标签、等宽哈希列和明显键盘焦点。本次 UI 技能搜索两次均返回 FAQ 落地页，不适合此产品；因此不采纳该页面布局，以下为按桌面工作流设计的方案。

左侧导航：项目与构建、名称浏览、发现任务、验证与冲突、导出、设置。

“发现任务”页面上方输入关键词；下方左栏设置资产类型、包范围、规则与候选预算；中央显示候选预览和任务表；右栏显示选中命中的来源、回算过程与资产包。底部状态栏显示后端、吞吐、已覆盖候选数、新增名称和剩余预算。

开始前显示目标未知资产数、规则空间大小、示例候选和估算时间。运行时支持暂停、恢复和取消，日志按批次合并，不逐候选刷新 UI。资产表使用分页/虚拟化，结果更新节流。状态除了颜色必须有文字；空结果、无 GPU、输入错误、源文件失效、内核失败、冲突和导出失败都有明确提示。

结果列表默认分开显示“已有名称命中”和“本次新发现”。过滤/搜索结果数不是发现进度。详情显示使用的算法、完整哈希、证据级别及构建。导出页提供仅新增/全部已验证、类型范围、合并冲突预览、输出目录和回读报告。

## 9. Saluki 导出方案

cod-name-db 明确提供 CSV 到 Saluki CDB 的转换工具：[项目 README](https://github.com/echo000/cod-name-db)。本地 `src/name_index_gen.rs` 使用 `porter_utils::NameDatabase`，CSV 没有表头，字段为十六进制哈希和名称，并支持 CDB 回转 CSV。

优先复用固定版本的转换器或同版本 porter-utils 接口，不能把通用 Unix cdb 或改扩展名当作 Saluki 文件。输出至少包含：已验证 CSV、Saluki `.cdb`、manifest.json（构建/算法/词典/条数/校验值）及审计 JSONL。CSV 使用正规引号转义；实际命名、目录、完整键或掩码键由指定 Saluki 版本源码/实机确定。

导出流程：冻结结果快照 → 合并并拒绝未处理同键异名 → 写临时 CSV → 转 CDB → 官方/匹配读取器回读 → 比对键值集合 → 原子落盘。所审计的当前 porter-lib 依赖保存时按名称排序，而本地转换器还留有 HashMap 顺序变化的旧 TODO；应锁定依赖并明确名称/哈希二级排序，以集合等价验收，另保存输出文件校验值。

最终兼容性必须在用户指定的 Saluki 版本中，用已知非模型资产和新发现非模型资产各验证名称显示；还要确认其 COD26 支持情况。生成可读名称数据库不等于为 Saluki 增加新游戏提取能力。尚未完成这一实机验收，方案不能声称已兼容。

## 10. 开发阶段与验收

估算为一名熟悉逆向及桌面开发的工程师约 6–9 周；属于工作量估计，哈希域和 Saluki 兼容研究可能延长。

| 阶段 | 预计时间 | 交付与退出条件 |
|---|---|---|
| P0 事实与格式锁定 | 3–5 天 | 锁定构建、profile、Saluki 版本、开源许可证；真实名称测试向量及小型 CDB 加载验证 |
| P1 CPU 查找闭环 | 1–2 周 | 只读导入、有限模板、Rust worker、严格验证、CSV/CDB；CLI 可重复运行 |
| P2 GUI 与后台恢复 | 1–2 周 | 任务页、结果表、托盘、暂停/恢复、预算、故障恢复；GUI 不阻塞 |
| P3 GPU 可选后端 | 1–2 周 | CUDA 自检、端到端基准、CPU 回算、异常回退；CPU/GPU 同空间结果一致 |
| P4 打包与实际验收 | 1–2 周 | Windows 可移植包、许可证清单、使用文档、Saluki 加载记录、真实未知目标试运行 |

第一阶段先做三个小实验：隐藏一批真实已知非模型名称（覆盖音频、动画等不同域），验证规则能找回；用若干已知映射完成 CDB 往返及 Saluki 加载；对同一有限候选空间比较 CPU/GPU，后者在 CPU 闭环完成后进行。

正确性验收：每个 profile 的真实样本全部回算一致；GPU/CPU 已测试空间命中集合一致；低 60 位伪匹配、冲突、错误 profile、坏数据不会进入发布；暂停/崩溃恢复与连续执行的结果集合一致；排除材质时目标及导出没有 material。

效果验收：将按非模型资产类型、名称家族及构建划分的已知名称作 holdout，避免训练词典泄漏被隐藏名称；报告固定预算下召回率、候选量和耗时。合成规则样本只测逻辑，不能代替真实未知名称发现效果。未知非模型资产的找回数量不作保证，全部隐藏名能找到也不能证明真实未知名都可找到。

可靠性验收：建议持续运行 8 小时（验收目标，尚未测试）、注入进程退出/设备失败/输出路径不可写，确认不丢已提交结果，磁盘增长与失败候选数量无关；导出回读集合相同且 Saluki 实际显示名称。

## 11. 风险、开源参考和后续范围

关键风险是算法/构建不匹配、候选空间爆炸、命名规律缺失、碰撞与规范化歧义、驱动可靠性和 Saluki 版本差异。解决顺序应是固定 profile 与目标 → 限定候选 → 独立验证 → 后台恢复 → 性能优化。

可参考 [Atian Tools README](https://github.com/ate47/atian-cod-tools/blob/main/README.md) 的哈希工具与索引流程，并检查 [GPU 调度源码](https://github.com/ate47/atian-cod-tools/blob/main/src/core/acts/tools/hashes/hash_gpu.cpp) 和 [OpenCL 内核](https://github.com/ate47/atian-cod-tools/blob/main/config/data/opencl/hashbrutegpu.cl)。不能直接假定这些实现已支持本机 COD26 哈希配置。Greyhound 名称索引用于 WNI 兼容，Cordycep 用于后续提取适配研究。

复用源码或分发数据库前核查具体文件/仓库许可证与固定依赖；公开仓库不自动意味着可任意复制或再分发。本工具默认本地导入已有游戏数据，保持源文件只读。

后续可加入构建差分、更多哈希域、规则共享、OpenCL、多 GPU、依赖关系辅助候选。AI 可以建议命名词和模板，但建议必须进入同一确定性回算链，不能以模型置信度代替验证。

建议先启动 P0/P1，目标是“关键词 → 有限候选 → 已验证命中 → Saluki 名称数据库”的最小完整闭环，随后完善界面和 GPU。

本地主要依据：`analysis/asset-catalog/资产目录说明.md`、`catalog-summary.json`、`assets.sqlite`、`resolve_asset_names.py`、`AssetWorkbench/core.py`、`analysis/cod-name-db/src/name_index_gen.rs`。公开来源补充见同目录 `github-research.md`。


## 12. 补充：音频路径扁平化（用户确认）

用户说明：导出音频文件名时，目录反斜杠 `\` 被替换成 `_`。这是导出阶段的规则，不等于哈希输入规范化规则。必须分别保存 exported_filename（导出名）、candidate_asset_path（候选原路径）、hash_input（算法规范化输入）。

示例 `weapons_mike4_fire_01.wav` 仅用于说明：其中下划线可能来自目录边界，也可能本来就在名称中。不能全局替换 `_` 为 `\`。应先利用词典已有目录、同家族前缀及包内字符串确定边界，再有限枚举不确定边界；n 个边界二选一会生成 2^n 候选，需限制边界数及预算。

本地 `fnv1a_english_xsounds.csv` 已看到 `vox/scripted/.../*.rn75.pc.en.snd` 形式。这表明部分词典使用内部路径、语言标识及内部后缀。导出的 `.wav` 不一定参与资产哈希，不能将播放器文件名直接用于回算，也不能对所有音频统一追加 `.snd`。声音别名、sndasset 名称及音频文件路径应建立独立名称域，并用样本确认关联。

P0 必须增加若干同一音频的完整哈希、导出文件名、原路径或包内字符串对照样本，核实路径扁平化、扩展名转换、重复文件名后缀和大小写处理。自动路径恢复仍需完整哈希验证。CDB 写入对应读取器期望的资产名称，扁平化文件名放旁表，不能未经确认写进名称数据库。

本地目录报告记录 sndasset 共 120,745 个，已命名 19,821 个，未命名 100,924 个；这是资产目录类型计数，不等于导出的音频文件数。此次首版覆盖所有非模型资产，音频路径恢复是其中需要专门适配的一条流水线。

## 13. 已审计的 CDB 与许可证补充

公开源码审计补充：CDB 为 PNDB 魔数、16 字节 little-endian 头、LZ4 raw block；解压内容为 N 个 NUL 终止名称字符串，之后为按相同顺序排列的 N 个 little-endian u64 键。详见 [github-research.md](github-research.md)。这些是格式依据，当前 Saluki 安装位置、键掩码与 COD26 支持仍须实测。

实际转换器依赖 echo000/porter-lib，审计发现 GPL-3.0；cod-name-db 未发现根 LICENSE。P0 锁定分发策略：选择符合项目许可目标的转换器使用方式，或依据公开格式独立实现并验证。不将外部程序调用自动当成免除许可义务的结论。Atian 的 CPU/GPU 模块可按具体文件及依赖许可选择参考。
